# Аудит: чего не хватает в seq_vps.sh

> **Статус на 2026-10-14: пункты 1.1, 1.3, 1.5, 2.1, 2.4, 2.5, 2.6, 3.1 и 3.3
> внедрены и проверены на живом стенде CT205** (этапы 16–19 и правки
> этапа 7). Ниже они оставлены с пометкой, что именно и как сделано.
> Ещё не сделано: 1.2 (origins автообновлений), 1.4 (PerSourceNetBlockSize),
> 2.2 (PAM внедрён частично — faillock есть, политика паролей только через
> pwquality), 2.3 (AllowUsers), 3.2 (отправка логов вовне), 3.4–3.8
> (AIDE/rkhunter/2FA/systemd sandboxing), Docker (частично — предупреждение).

Дата: 2026-10-14. Источники — ресёрч по актуальным чек-листам харденинга Linux
(2026: CIS Benchmarks for Ubuntu 24.04 / Debian 13, гайды по sysctl, PAM,
auditd, systemd-санитайзингу, SSH 2026) плюс проверка по коду скрипта и
локальные проверки `sshd -T` / `sysctl` на этой машине.

Всё, что отмечено «проверено», проверялось локально на OpenSSH 10.6 и текущем
Debian-хосте; поведение на чистом VPS ещё предстоит подтвердить.

---

## Что у скрипта уже есть (не трогать)

- Drop-in `00-seq-vps.conf` с объяснением приоритета; `sshd -t` до каждой
  записи в конфиг; `KbdInteractiveAuthentication` вместе с
  `PasswordAuthentication`; сокет-активация `ssh.socket`.
- UFW/firewalld по дистрибутиву, SELinux-порт и `restorecon`.
- Fail2Ban с выбором backend, CrowdSec с коллекцией `sshd`.
- unattended-upgrades / dnf-automatic, BBR, Lynis, бэкапы каждого файла,
  откат этапа.
- Свежее: встроенный rate-limit OpenSSH 9.8+ показывается в этапе 5.

## 1. Мелкое — можно закрыть в тот же день

| # | Пробел | Почему важно | Как закрыть |
|---|--------|--------------|-------------|
| 1.1 | ✅ **UFW не включает IPv6** | Скрипт бэкапит `/etc/default/ufw`, но `IPV6=yes` не выставляет. С выключенным IPv6 правила UFW не покрывают IPv6, а сервер с AAAA-записью доступен по нему напрямую | в этапе 7: проверить `grep '^IPV6=yes' /etc/default/ufw`, выставить при необходимости, `ufw reload` |
| 1.2 | **SOCKS-профиль unattended-upgrades и origins** | На Ubuntu 24.04 `50unattended-upgrades` содержит `origin=Ubuntu,codename=${distro_codename}` (все обновления), а не только `-security`; скрипт это не проверяет | этап 8: показать фактические `Allowed-Origins`, при желании сузить до `-security`/`-updates` |
| 1.3 | ✅ **Docker обходит UFW** | Публикуемые порты контейнеров открываются в обход правил UFW (`DOCKER-USER`), очень частый сюрприз на VPS | этап 7: если `command -v docker`, предупредить и показать `DOCKER-USER`-правило или `ufw-docker` |
| 1.4 | **Нет порога для `PerSourceNetBlockSize`/`PerSourceMaxStartups`** | Встроенный rate-limit есть, но за CGNAT один шумный источник банит весь /32 | информационный пункт рядом с 7 (только показ значений) |
| 1.5 | ✅ **`/etc/sudoers.d` не аудитируется** | Доп. правила sudo — популярный способ тихой эскалации (CVE-2025-32463 «sudo chroot») | новый пункт в этапе 2: `visudo -c`, список `NOPASSWD`, проверка версии sudo ≥ 1.9.17p1 |

## 2. Среднее — новые пункты и разделы

| # | Пробел | Почему важно | Форма |
|---|--------|--------------|-------|
| 2.1 | ✅ **Внедрено: этап 16 «Харденинг ядра»** — было: нет sysctl-харденинга | В скрипте `sysctl` только для BBR. Актуальные чек-листы требуют: `fs.suid_dumpable=0`, `kernel.kptr_restrict=2`, `kernel.dmesg_restrict=1`, `fs.protected_{hardlinks,symlinks,regular}`, `kernel.yama.ptrace_scope=1`, `net.ipv4.conf.all.{accept_redirects,send_redirects,accept_source_route}=0`, `net.ipv4.tcp_syncookies=1`, `net.ipv4.ip_forward=0` (если не роутер) | новый **этап 16 «Ядро (sysctl)»**: показать текущие значения, применить рекомендуемые в `/etc/sysctl.d/99-seq-vps.conf`, каждое значение отдельно включаемое, валидация через `sysctl -n` перед записью |
| 2.2 | **Нет PAM: блокировка аккаунтов и парольная политика** | `pam_faillock` (локальный лок-аут), `pam_pwquality` (сложность). Отдельный слой к Fail2Ban: тот банит источник, этот — учётку. На Ubuntu `pam-auth-update`, на RHEL `authselect` | новый **этап 17 «Пароли и блокировки (PAM)»** с бэкапом `/etc/pam.d/*` и откатом; по умолчанию показывать и предлагать, не включать молча (риск залочить root) |
| 2.3 | **Нет allowlist пользователей SSH** | `AllowUsers`/`AllowGroups` — один из самых эффективных «спящих» пунктов: аккаунт вне списка не войдёт даже с валидными данными. Скрипт этого не предлагает | пункт в этапе 5: сформировать `AllowUsers` из обычных пользователей, показать итог, применить через `_ssh_apply` (валидация до записи — механизм уже есть) |
| 2.4 | ✅ **Нет проверки «кто слушает наружу»** | Список открытых портов + процессов — самый быстрый способ найти лишнюю службу | новый безобидный этап «Аудит: что слушает» (`ss -tulpn`, отметка портов не из фаервола) |
| 2.5 | ✅ **Нет аудита учётных записей** | Пустые пароли, UID 0 кроме root, аккаунты с шеллом без пароля | пункт в этапе 2 или отдельный аудит: `awk -F: '$3==0'`, `passwd -S`, `lastlog` |
| 2.6 | ✅ **Нет аудита файловой системы** | World-writable файлы, SUID/SGID, пустые пароли | аудит-этап: `find / -xdev -perm -4000`, `-type f -perm -0002` (с исключениями `/proc`, `/sys`) |

## 3. Крупное — отдельные подсистемы

| # | Пробел | Почему важно | Объём |
|---|--------|--------------|-------|
| 3.1 | ✅ **Нет auditd** | Ядровой аудит: запись в `/etc/passwd`, `/etc/sudoers`, `execve` от root, загрузка модулей. Аудиторский след — то, без чего разбор инцидента невозможен. Основной пробел среди «крупного» | новый этап: установка, `rules.d/seq-vps.rules` (baseline), `augenrules --load`, проверка `ausearch -k`, предупреждение о ротации/удалённой отправке логов |
| 3.2 | **Нет отправки логов вовне** | Root может очистить локальные логи; remote syslog — то, что нельзя подчистить | подпункт к auditd/этапу 9: показать, как настроить `rsyslog`/`journald` forward, проверить доступность |
| 3.3 | ✅ **Нет проверки AppArmor** | На Ubuntu/Debian LSM есть, профили могут быть в complain/не загружены. `aa-status`, включение `apparmor` | аудит-пункт: показать статус, число профилей, непринуждённые процессы |
| 3.4 | **Нет проверки целостности файлов (FIM)** | AIDE/Tripwire — базовый ответ «что изменилось в /etc с прошлого прогона» | этап по желанию: установка AIDE, `aideinit`, запуск сравнения, отчёт |
| 3.5 | **Нет проверки rootkits** | `rkhunter`/`chkrootkit` — быстрый скан на известные руткиты и странности | пункт-аудит в этапе 13 (Lynis) — не заменяет Lynis, дополняет |
| 3.6 | **Нет 2FA для SSH** | TOTP через `google-authenticator` + `AuthenticationMethods` — заметно поднимает планку при утечке ключа | отдельный пункт этапа 5 с очень осторожным применением (требует второй фактор на тестовом подключении) |
| 3.7 | **Нет проверки целостности пакетов** | Изменённые бинарники: `debsums`/`rpm -Va` | пункт-аудит, отчёт «изменённые/неподписанные файлы» |
| 3.8 | **Нет sandbox-подсказок для своих сервисов** | `systemd-analyze security <unit>` показывает EXPOSURE; drop-in с `ProtectSystem`, `NoNewPrivileges`, `PrivateTmp`, `CapabilityBoundingSet` | информационный пункт: прогнать по юнитам и показать топ по экспозиции, без правок |

## 4. Отдельная тема: Docker

Если на сервере есть Docker, привычная модель «фаервол + Fail2Ban на хосте»
частично рассыпается: публикуемые порты обходят UFW, а CrowdSec/Fail2Ban видят
только трафик хоста. Это не баг скрипта, но об этом честно нужно сказать в
меню/README: проверка `command -v docker` и предупреждение в этапе 7.

## 5. Порядок внедрения

1. **Мелкое (1.1–1.5)** — правки внутри существующих этапов, каждая в отдельном
   коммите, всё проверяемо на тестовой машине.
2. **sysctl (2.1)** — самый большой выигрыш на строку кода: аудит + отдельно
   включаемые значения, ничего не ломает при отказе.
3. **AllowUsers (2.3)** и **аудит-этап (2.4–2.6)** — читающие проверки, почти без
   риска; дают владельцу сервера видимость.
4. **PAM (2.2)** — после тестового прогона: риск залочить доступ, нужен
   аккуратный бэкап и откат.
5. **auditd (3.1) + FIM/rootkit/AppArmor (3.3–3.5, 3.7)** — «наблюдаемость»;
   логично делать после того, как доступ и защита уже настроены.
6. **2FA (3.6)** и **systemd sandboxing (3.8)** — по желанию, как отдельные
   расширения.

## Чего в списке сознательно нет

- **CIS-профили целиком** (`usg`, `openscap`): они ломают рабочие сценарии
  (USB-хранилища, монтирования, IPv6-стек) и требуют исключений под конкретный
  сервер. Скрипт по духу — «разумный минимум с объяснением», а не аудит на
  соответствие.
- **Антивирус/EDR, honeypot, port-knocking**: вне задачи харденинга VPS по
  умолчанию — это отдельные решения и отдельные риски.
